## Idea
Supersede all prior frontend directions with a new, independent `themes/rural-up-theme` copied from `themes/hotel-reservation-theme`, while preserving `my-farmhouse-child-theme` unchanged for reference and rollback. Deliver a production-ready Phase 1 visual redesign in four weeks for the current QloApps functionality: a coherent 2026 editorial-rural-modern digital identity under the provisional Rural UP name; Airbnb-like warmth with Booking.com-like utility; one responsive WCAG 2.2 AA theme for mobile, tablet, and desktop; account-required instant booking; existing one-page checkout; enabled offline payment states; regions, informational activities, and stories; consent-ready privacy UI; licensed self-hosted editorial imagery that never misrepresents individual properties; and complete booking-first regression coverage. Preserve every QloApps hook, Smarty variable, form field, selector, JavaScript behavior, payment slot, and translation contract. Prior redesign implementation and decisions are not carried forward automatically. Phase 2, outside the four-week release, will introduce property-first global search, availability/relevance ranking, functional marketplace filters, account-synced favorites, and only unavoidable module-owned schema. Indian gateway and pay-at-property modules are separate security-sensitive workstreams requiring approval before booking/payment changes. No map, AI, public ownership claims, government emblems, or multi-property cart at launch.

## Implementation
- Establish a read-only baseline inventory before implementation: record active theme/configuration, enabled modules, hook and selector contracts, configured OPC branch, account-required checkout, payment states, responsive/mobile settings, reachable customer routes, current performance, and existing worktree changes; define the exact Phase 1 acceptance matrix and Phase 2 boundaries.
- At Milestone 1, create two coded responsive identity concepts using the provisional Rural UP name, each with a wordmark and symbol, editorial-rural-modern art direction, color/type/icon/motion tokens, landscape-and-lived-detail photography rules, content voice, English-first translation-safe typography, and representative home/search/card/checkout components; review and approve one direction before broad implementation.
- After identity approval, copy the untouched `themes/hotel-reservation-theme` into a new independent `themes/rural-up-theme` without modifying or deleting the default or `my-farmhouse-child-theme`; update only the reviewed theme registration/selection and explicitly disable the legacy mobile-theme path so one responsive theme serves all devices.
- Build the approved design-system foundation with self-hosted fonts and one coherent licensed icon family; define reusable layout, typography, color, spacing, radius, elevation, forms, buttons, cards, badges, loading/empty/error states, focus, reduced-motion, bottom navigation, header, footer, breadcrumb, pagination, modal/drawer, and responsive primitives while retaining Bootstrap and legacy selectors required by QloApps JavaScript.
- Redesign the shared shell and homepage using the approved identity: desktop/mobile navigation, mobile bottom navigation, destination-dates-guests search presentation, trust and support cues, scalable featured-property cards, regions, informational activities, stories, consent-ready UI, and phone/email/WhatsApp support deep links; preserve all existing hooks and keep the current hotel-first search behavior in Phase 1.
- Redesign the existing discovery and booking surfaces without changing backend behavior: properties directory, category/availability results, sorting and existing amenity/price filtering, property/room detail, galleries, verified-stay ratings, per-rate cancellation presentation, nightly from-price and date-aware totals, occupancy, services, availability/unavailable states, cart, and booking forms; use designed placeholders for properties without authentic media.
- Redesign and validate the configured account-required one-page checkout only: authentication/registration, account details needed for booking, cart summaries, guest and address forms, terms, payment option cards, current bankwire/cheque execution and return states, validation failures, confirmation, and post-booking support; preserve payment hooks for later Indian gateway and pay-at-property modules without altering booking or payment logic.
- Complete all relevant customer surfaces to a consistent baseline after the booking journey: account dashboard, identity, addresses, booking history/detail, refunds/returns/slips/vouchers where enabled, password recovery, contact/help, CMS/legal/content-only pages, regions, activities, blog list/detail, newsletter responses, sitemap, 404, maintenance, restricted-country, empty/no-results, and generic errors; retire irrelevant retail-era routes through separately reviewed safe redirects rather than redesigning them.
- Source and download commercially licensed editorial placeholder images from approved providers, optimize and self-host them with source/license records, use landscape/architecture/food/craft details without identifiable faces, never present generic stock media as a specific property, add responsive dimensions and lazy loading where appropriate, and provide provisional translated-ready copy plus a content replacement guide.
- Run milestone QA in the local seeded Podman stack at phone, tablet, and desktop widths across modern browser engines: full home-to-confirmation booking regression, logged-out/logged-in states, hooks and DOM contracts, keyboard and screen-reader semantics, WCAG 2.2 AA checks, no horizontal overflow, long-text/Hindi-readiness checks, console/PHP errors, and Core Web Vitals targets of LCP <=2.5s, INP <=200ms, and CLS <=0.1; perform a staging smoke test when access exists.
- Document the approved identity, component usage, template/module override rules, media provenance, content operations, support and consent integration points, route redirects, QA evidence, known seeded-data limitations, cache/runtime procedure, and Phase 2 backlog; obtain final Phase 1 approval before activation.
- Plan Phase 2 as separate reviewed feature work: property-first destination results with one-property-per-booking, availability/relevance ranking, region/distance/amenity/stay/activity filters mapped onto existing admin data where possible, account-synced favorites, scalable demo fixtures, and minimal module-owned tables only where unavoidable; separately specify and approve the Indian payment gateway and pay-at-property modules before any schema or booking/payment implementation.
